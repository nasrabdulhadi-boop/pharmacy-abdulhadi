## نطاق العمل

- قاعدة QA حصراً: `vpjxdsprfcpqclnhbeoh`.

- جميع الأصناف والحسابات والحركات المضافة اصطناعية. لم تُستورد بيانات مرضى أو مبيعات أو موردين حقيقيين.
- حسابات الموظفين والدعم السابقة لم تتغير. أنشئت أربعة حسابات اختبار مستقلة: مدير، موظف، دعم فني، وحساب بلا دور.

## ما أُصلح

1. ثغرة مؤكدة: كان شرط `role <> 'employee'` و`role NOT IN (...)` يتعامل مع NULL بطريقة تسمح لحساب بلا دور بتجاوز المنع. أُثبتت داخل معاملة ملغاة وأُصلحت بشروط تفشل بصورة مغلقة.
2. بوابة الموظف كانت ترسل `p_action` بينما الدالة تتطلب `p_operation`. استبدل المسار بنموذج مرتبط بعقد API صحيح.
3. سحب دور الموظف لم يكن يخفي بالضرورة طلباته السابقة. أصبحت القراءة تتطلب الدور الحالي مع ملكية الطلب أو دور المدير.
4. جميع صلاحيات QA المحمية تعتمد على دور الحساب الحالي وجلسة Auth حية؛ تسجيل الخروج العام يمنع إعادة استخدام JWT القديم فوراً عند حدود قاعدة البيانات.
5. الدور الصريح NULL أو غير المعروف لا يرث صلاحية legacy admin. تعديل user_metadata لا يمنح دوراً.
6. أُصلح تعارض اسم متغير SQL ظهر عند أول تنفيذ للمشتريات؛ أُعيد الاختبار بنجاح.
7. الجرد المبني على رصيد قديم كان يثير خطأ serialization مع تعثر زمني عبر HTTP. تغير إلى خطأ تحقق واضح، وأثبتت إعادة الاختبار رفضه دون آثار جزئية.
8. التشخيص المنقح يعرض unknown على الخادم بدلاً من إعطاء انطباع صحي غير مثبت.
9. ثُبتت إصدارات الاعتماديات بملف lock، وأُضيفت اختبارات src التي كانت خارج أمر npm test إلى الفحص المستمر.

## ما أصبح متاحاً في المختبر

واجهة عربية مستقلة للمدير والموظف، مع نموذج تعيين كلمة مرور QA للحساب الحالي بعد التحقق منه؛ تفعيل النموذج محصور في إعداد staging المطابق لمشروع QA. لم يُختبر إرسال بريد الاسترداد أو تغيير كلمة مرور المستخدم بصرياً بعد. تشمل الواجهة: الأصناف والأرصدة المتاحة، إرسال طلبات البيع والجرد والشراء الآجل والمرتجع ومعالجة الطلب، تفاصيل المراجعة، الموافقة والرفض، مستندات التنفيذ وتقارير المدير بعملات منفصلة.

الموافقة على طلب يحمل `sandbox=true` تنفذ آثاره على مخطط `pharmacy_qa_private` فقط. الطلبات القديمة بلا تفاصيل تظل طلبات حالة فقط. لا تُستخدم الجداول المالية أو دوال البيع الأصلية في هذا المختبر.

- البيع: أسعار الخادم، أجزاء العبوة، FEFO، استبعاد المنتهي، تكلفة فعلية من الدفعات، ومنع تجاوز الرصيد.
- الشراء: بونص وخصم، بونص فقط، دين مورد اصطناعي منفصل USD/SYP. البونص لا يضاف إلى قيمة الفاتورة.
- الجرد: مقارنة لقطة الرصيد وقت الموافقة لمنع اعتماد جرد قديم.
- المرتجع: يرتبط ببيع الموظف الأصلي، يعيد الكمية إلى الدفعات الأصلية، يمنع تجاوز الكمية المباعة تراكميّاً، ويعكس قيمة البيع والتكلفة.
- القرار: قفل الطلب وقفل العمليات لكل صنف، التنفيذ مرة واحدة، وكل التنفيذ داخل معاملة واحدة؛ الفشل لا يترك مستنداً أو مخزوناً أو قيداً جزئياً.
- الموظف: يرى طلباته ومستنداته التشغيلية فقط؛ لا يقرأ التقارير الإجمالية أو يغير أسعار البيع أو يقرر الطلبات.
- الدعم الفني: حالات تقنية ثابتة ومنقحة للقراءة فقط؛ لا أصناف داخلية أو طلبات أو تقارير أو عمليات مالية.

## الحدود والمتبقي

1. **تسليم دخولك الشخصي:** نحتاج بريد QA مستقل تتحكم به لتعيين طريقة دخول آمنة. حساب المدير الآلي الحالي مجرّب فعلياً، لكن بريده اصطناعي. لا تُرسل كلمة مرور في المحادثة.
2. **قبول المتصفح بعد الدخول:** اختبار الإرسال والقرار والرفض من الواجهة، قياس العرض على الهاتف والحاسوب، ومراجعة حالات الخطأ بصرياً. تسجيل الدخول وطلبات HTTP نجحت؛ هذا لا يعادل قبول الواجهة كاملة.
3. **اختبارات النظام الأصلي:** المختبر الجديد ليس نسخة مطابقة لمخطط الإنتاج. ربط صلاحيات التشغيل بدوال نقطة البيع والمشتريات والتقارير الأصلية، واختبار الديون والمدينين والصندوق وكل سيناريوهات النظام الأصلي على مخطط QA مطابق، ما زال غير منجز. لا يُستخدم نجاح المختبر كدليل على جاهزية تلك الأقسام.
4. النسخ الاحتياطي والاستعادة والبريد التشغيلي والتشخيص الحي ليست مكتملة بهذه الدفعة. لا توجد نتيجة استعادة أو إرسال بريد ناجحة مُدّعاة.
5. في المختبر: زيادة الرصيد بالجرد تستخدم تكلفة صفر، والمشتريات آجل فقط، ومعالجة الطلب حالة تشغيلية دون بيانات زبون. لا تستخدم تقاريره لأرباح الصيدلية.
6. فحص Supabase ما زال يعرض 16 تحذيراً لدوال SECURITY DEFINER المسموح تنفيذها للمصادقين. هذه واجهات مقصودة ومقيدة بالدور والجلسة، لكنها تبقى سطحاً يحتاج مراجعة قبل الإنتاج. الجداول الخاصة مفعّل عليها RLS ولا تملك أدوار API أي صلاحيات مباشرة عليها؛ عدم وجود policies مقصود لمنع الوصول المباشر.
7. حماية كلمات المرور المسربة غير مفعلة على QA. لم نغير إعدادات أو خطط مدفوعة.

إرشادات التحذيرات: [الدوال ذات الصلاحية المرتفعة](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable)، [حماية كلمات المرور](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

## إعادة التنفيذ للمطور

ملفات SQL في `audits/qa/` توثيق قابل للمراجعة للتغييرات المطبقة على QA فقط، وليست migrations للإنتاج. ترتيب تطبيقها على البيئة الصحيحة: `authorization_functions.sql` ثم `operational_sandbox.sql` ثم `session_and_role_revocation.sql`.

تحتاج scripts/qa ملف حسابات اصطناعية خارج المستودع ومتغير QA_PUBLISHABLE_KEY. يجب تجهيز كلمات المرور عبر Auth Admin API على الخادم؛ لا تُنشأ حسابات بكلمات مخمنة ولا يُعدّل مستخدم إنتاج. تستخدم إعادة اختبارات العمليات مجموعة أصناف جديدة برصيد ابتدائي 35 منها 5 منتهية، وأسعار وتكلفة seed المطابقة للملف SQL؛ يدعم QA_FIXTURE_SUFFIX عزل كل تشغيل. لا تُصفّر سجلات سابقة أو بيانات المستخدم من أجل إعادة الاختبار.

لا توجد كلمات مرور أو access/refresh tokens أو service-role keys في هذه الملفات. أداة تجهيز الحسابات المؤقتة أُغلقت بعد استخدامها، وأعيد تفعيل verify_jwt عليها.
