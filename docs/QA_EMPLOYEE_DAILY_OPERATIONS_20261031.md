# العمليات اليومية المباشرة للموظف — QA فقط

تحديث الصلاحيات المعتمد من المستخدم في 31 أكتوبر 2026 يحل محل قاعدة «كل العمليات تنتظر المدير» في التقارير السابقة. التطبيق محصور بفرع `feature/system-administration-center-preview-20261028` ومشروع `vpjxdsprfcpqclnhbeoh`. لم يتغير main أو مشروع الإنتاج أو حساب المدير الأصلي.

## السلوك الحالي

| العملية | الموظف في QA |
|---|---|
| البيع النقدي بالسعر المعتمد، والكمية ضمن الرصيد | تنفيذ مباشر مع خصم المخزون وتسجيل الصندوق في معاملة واحدة |
| شراء آجل جديد من المورد الاصطناعي | تنفيذ مباشر مع الكمية والبونص والصلاحية وخصومات الشراء ودين المورد |
| إضافة بطاقة منتج جديدة من المنتجات أو فاتورة الشراء | مباشر، مع حفظ البيانات الأساسية ومنع تكرار الباركود |
| إدخال كميات الجرد ومسودته | مسموح؛ تطبيق فروق الرصيد ينتظر المدير |
| المرتجعات | تنتظر المدير |
| تغيير سعر منتج موجود أو رصيد مباشر أو الموافقات | ممنوع على الموظف من الخادم |
| الصندوق اليدوي ودفعات الموردين والبيع الآجل وإدارة الحسابات | خارج صلاحيات الموظف / غير مربوط في QA |
| الدعم الفني | الحالة التقنية المنقحة فقط؛ لا تغيير لصلاحياته |

تسجيل تكلفة شراء جديدة لا يفتح تكاليف المخزون أو الأرباح للموظف. قراءة تفاصيل مشترياته التشغيلية تبقى ضمن سجلاته. لا تُرسل له حقول تكلفة المخزون أو التقارير الإجمالية في snapshot.

## حد التسعير الواضح

لا توجد في QA قاعدة مركزية معتمدة لتسعير بطاقة جديدة. بدلاً من اختراع نسبة أو منح تعديل الأسعار، يحفظ الموظف البطاقة دون سعر بيع مفعّل، ويعتمد المدير السعر أولاً. يمنع الخادم بيع البطاقة بسعر صفر. يمكن تسجيل شرائها آجلاً قبل تفعيل سعرها، دون السماح بتعديل سعر منتج موجود أثناء الشراء. لم تُغير أسعار المنتجات الموجودة تلقائياً.

الباركود الأساسي يعمل؛ الباركودات الإضافية لم تكن مربوطة في مخطط QA، وتُرفض صراحة دون حفظ جزئي. لم تُحذف أو تُغيَّر بنية الباركودات في الإنتاج.

## التنفيذ وحماية البيانات

- دالة `qa_employee_execute_workspace` لا تسمح إلا بالبيع والشراء اليوميين. تفحص الدور والجلسة الحية على الخادم، وتستخدم منفذاً خاصاً لا يملك أدوار API حق استدعائه. لم يُمنح الموظف is_admin أو صلاحيات مراجعة المدير.
- الجرد والمرتجع يحتفظان بمسار `qa_submit_workspace_bundle` والمراجعة الأصلية للمدير. الدالة العامة لموافقة المدير بقيت على شرط المدير.
- لكل حفظ مباشر مفتاح إعادة محاولة؛ تكرار المفتاح والبيانات يعيد العملية الأصلية. اختلاف البيانات مع المفتاح نفسه يُرفض. الأقفال ومعاملة قاعدة البيانات تمنع خصم بعض الأسطر أو ازدواج أثر نفس المحاولة.
- حفظ فاتورة الشراء يحفظ رأسها ويرفض تكرار رقم المورد أو حقن دفعة مالية أو تاريخ سابق. تجميع أسطر الفاتورة في عرض واحد يحفظ رقمها وبونصها وصلاحياتها.
- إنشاء البطاقة يحفظ البيانات في جداول QA الموجودة ويربطها بالكتالوج الاصطناعي. لا إضافة أو حذف جداول أو أعمدة أو تعديل قيود أو سياسات RLS أو منح وصول مباشر للجداول. الدوال فقط أُضيفت/حُدّثت.
- التحويل إلى SYP وFEFO والتكلفة الفعلية تظل من الخادم. فشل أي سطر يلغي المستندات والحركات والقيود كلها.
- أُضيف قفل حفظ لفاتورة البيع، وتوحيد الطلبات المتزامنة، ورسائل واضحة للعمليات غير المسموحة. أعيد استخدام النماذج الأصلية، بما فيها إضافة منتج من داخل الشراء.

ملف `audits/qa/employee_daily_operations_acceptance.sql` يختبر باستخدام claims لحسابات Auth اصطناعية ذات جلسات حقيقية، داخل اتصال SQL موثوق، ويُلغي بيانات الاختبار كاملة. هذه ليست اختبارات توقيع JWT عبر HTTP أو اختبارات متصفح.

بدأت فحوص HTTP بحسابات جديدة، لكنها توقفت بسبب حظر proxy لاتصال بيئة العمل؛ لا تُسجل دورة HTTP ناجحة كاملة لهذه الدفعة. يوجد سكربت قابل للإعادة `scripts/qa/daily-operations-acceptance.mjs` بعد استعادة الاتصال وتجهيز حسابات اختبار جديدة. فحوص HTTP السابقة تبقى أدلة للإصدارات السابقة ولا تُنسب إلى هذا التحديث.

أُغلقت أداة تجهيز الحسابات مع تفعيل JWT بعد الاستخدام، وعُطلت حسابات الاختبار الأربعة وألغيت جلساتها. لم يُطلب أو يُستخدم سر المستخدم الشخصي.

راجعنا مستشار الأمان: بقيت تنبيهات الدوال SECURITY DEFINER القابلة لاستدعاء authenticated وحماية كلمات المرور المسربة غير المفعلة، ومعلومة RLS دون سياسة. الدوال الجديدة محكومة بالدور والجلسة ولا تمنح وصولاً للجداول؛ لم تُضعف إعدادات Auth لمعالجة الاختبارات.

هذه النسخة ليست إعلان جاهزية للإنتاج. يبقى اختبار الدخول التفاعلي الكامل ومسارات الإنتاج الأصلية خارج نطاق البرهان الحالي. الشراء المباشر الحالي آجل وللمورد الاصطناعي فقط، ولا يمثل ربط جميع الموردين والمدفوعات الأصلية.
